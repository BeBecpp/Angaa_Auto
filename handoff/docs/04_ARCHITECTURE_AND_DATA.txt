ARCHITECTURE AND DATA CONTRACT
Target: one shop, modular Laravel monolith. No microservices, tenant billing or separate frontend backend split.

1. RUNTIME AND PACKAGE POLICY
PHP 8.4 target; Laravel ^13.0; Filament ^5.0; compatible Livewire 4; Tailwind >=4.1; Composer 2; a supported Node LTS compatible with resolved Vite. Resolve and commit exact Composer and npm locks at implementation time; this specification has not executed that resolution. Check composer validate, composer check-platform-reqs, actual package constraints and official docs. Use current Filament schemas/actions/policies APIs, not copied v3 signatures.
Local default: SQLite file database, database cache/queue, private filesystem, SMS log adapter, optional mail log/Mailpit. Optional Docker Compose MySQL 8.4 test profile. MySQL target must use utf8mb4 and consistent UTC connection/app assumptions. Avoid MySQL-only ENUMs and raw SQL in ordinary domain code; use PHP backed enums stored as strings. SQLite success does not prove MySQL locking.
App timezone/database timestamps UTC; business.timezone Asia/Ulaanbaatar for display, forms, recurrence and quiet hours. due_date is a business-local date, not an arbitrary midnight UTC instant. Send ISO8601 event instants with explicit offset/Z; use a compatible named-timezone calendar integration or verified offset handling. Viewer device timezone must not change booking time.
Production queue can remain database-backed for a small shop; Redis optional later. Do not require Horizon with the database driver. Storage is behind Laravel filesystem; future private S3-compatible object storage uses the same visibility contract.

2. CODE ORGANIZATION (GUIDANCE, NOT MANDATORY CLASS COUNT)
app/Actions/Requests: SubmitServiceRequest, ConvertRequest.
app/Actions/Scheduling: ConfirmAppointment, RescheduleAppointment, CheckInVehicle.
app/Actions/Workshop: TransitionWorkOrder, PublishInspection, PublishEstimateRevision, RecordEstimateDecision, CompleteQualityCheck, DeliverVehicle.
app/Actions/Finance: IssueInvoice, RecordPayment, ReversePayment.
app/Actions/Maintenance: EvaluateDuePlans, PlanNotifications, DispatchOutbox.
app/Contracts: SmsProvider; app/Services/Messaging adapters; app/Policies for every sensitive aggregate.
app/Filament for staff resources/pages/widgets; app/Livewire for public/customer/mechanic screens; app/Http/Requests for request validation; app/Jobs for media processing and messages; lang/mn for translation.
Use actions/domain services shared by Filament, Livewire and commands. A form/controller must not bypass scheduling/approval checks. Money and status transitions are server-side. Avoid generic repository layers and unnecessary event buses.

3. DATABASE ENTITIES
Use internal primary IDs plus public random ULIDs/UUIDs where exposed. Public IDs reduce guessing but never replace authorization. created_at/updated_at where appropriate; explicit business timestamps below. Index all FK and common filter columns. Use restrictive FK deletion for history/finance; archive rather than cascading sensitive historical records.

users: id, type(staff/customer), name, email nullable, phone_normalized nullable, phone_verified_at, password nullable for customer-only identities, staff_role nullable, active, timestamps. Unique canonical verified login phone where present and unique staff email; policies strictly exclude customers from staff panel. No customer role escalation through mass assignment.
customers: id, user_id nullable unique, display_name, contact_phone, normalized_contact_phone, notes_internal, archived_at. Contact numbers need not be unique: households/company phones may be shared. First OTP sign-in does not auto-claim every customer with that phone. Staff explicitly links an existing customer after identity verification/intake invitation. New users can create a new customer identity; merging is audited, owner-controlled and never by phone alone.
vehicles: id, public_id unique, make, model, year nullable, vin nullable, current_plate_display/normalized, archived_at. Plate is not permanent identity; no mandatory globally unique plate constraint. VIN uniqueness only when a valid nonempty VIN is deliberately recorded; conflicts flagged for staff review. No raw full VIN in public UI by default.
vehicle_customer_access: vehicle_id, customer_id, relationship(owner/driver/fleet_contact), starts_at, ends_at nullable, verified_by/at, source. Current access is explicit and revocable, not inferred from a submitted plate. History still restricted by work_orders.customer_id and approved scope; association alone does not disclose all old work orders.
odometer_readings: vehicle_id, km integer nonnegative, observed_at, source(staff/customer), verification_state, recorded_by, correction_of_id nullable, note. Never silently replace earlier readings. Latest verified chronological reading drives due-by-km; overrides require audit.
services: id, slug unique, name_mn, summary, description, active/published, price_type(fixed/from/inspection_required), price_mnt nullable, estimated_duration_min nullable, buffer_min, category, sort_order. No default maintenance interval unless owner deliberately configures a vehicle/service-specific recommendation.
service_requests: public_id, guest_session_id/hash, idempotency_key unique per session, request_type, name/phone and vehicle text snapshots, symptoms, preferred_local_date/window, location/address nullable, contact_consent_at/version, reminder_preference, status, assigned_staff_id, first_responded_at, converted_appointment_id/order_id nullable, timestamps. Store uploads separately; do not automatically link an existing customer or car based on unverified text.
shop_bays: id, name, active, supported_categories; staff_profiles: user_id, display_name, bookable, capabilities.
opening_rules: scope shop/bay/mechanic, weekday, local_start/end, active period. closures: scope/id, starts_at/ends_at, reason. These can be appropriately normalized simple tables, not a generic rule engine.
appointments: public_id, request_id nullable, customer_id, vehicle_id nullable, type, requested/confirmed etc status, planned_start/end UTC, bay_id nullable, mechanic_user_id nullable, buffer/travel_min, confirmed_at/by, cancellation_reason, version counter, timestamps. appointment_services pivot or snapshot line items.
resource_reservations: appointment_id nullable, work_order_id nullable, resource_type(bay/mechanic), resource_id, starts_at/ends_at, active/status, actual_occupied_from/to nullable, version. Generic resource IDs must be validated against actual resource tables; alternatively use separate bay/mechanic reservation tables with proper FKs. Avoid pretending a polymorphic DB FK enforces types. Time interval index (resource_type, resource_id, starts_at, ends_at).
work_orders: public_id, unique order_number, request_id nullable, appointment_id nullable, customer_id, vehicle_id, status, assigned_mechanic_id, complaint, intake_km, customer/vehicle/contact snapshots, received/diagnosed/ready/delivered timestamps, promised_ready_at, owner_override fields, current_approved_estimate_revision_id nullable, cancellation/reopen fields. Historical snapshot decouples a former owner's record from a new owner's data/plate.
work_order_status_events: work_order_id, from/to, actor, reason, occurred_at. Append-only transitions.
inspection_items: work_order_id, template label snapshot, condition, finding_internal, finding_customer, published_at, checked_by/at. Templates can be config/table; persist the inspected label as snapshot.
media: public_id, uploader/session, exact parent type/id or typed FK, disk, private_path, preview_path, mime, byte_size, width/height, category(before/during/after/intake/request), inspection_item_id nullable, caption, customer_visible, processing_status, checksum, captured_at if verified, created_at. Denormalized parent references require scoped policies and parent existence validation. Random file paths; no original filenames in public URLs.
estimate_revisions: work_order_id, revision_number, state(draft/sent/approved/declined/superseded/expired), currency=MNT, totals, terms, valid_until, published_at, content_hash, timestamps. Unique(order_id, revision_number); sent+ documents immutable.
estimate_lines: revision_id, kind(labor/part), description, quantity scaled integer or DECIMAL with documented precision, unit_price_mnt integer, discount_mnt, tax_mnt if configured, total_mnt integer. Central documented rounding once per line; server totals only.
estimate_decisions: revision_id, decision, channel(portal/phone/in_person/owner_override), actor_user_id, customer_id, decided_at, amount_snapshot, content_hash, staff attestation note if phone, minimal security metadata per retention policy. Never label staff phone note as customer electronic signature. Idempotent unique decision per revision; explicit owner override remains separate from customer consent.
repair_items: work_order_id, approved_estimate_line_id nullable, description, work_done, quantity, cost_mnt nullable, completed_by/at; qc_checks: work_order_id, item snapshot, result, checked_by/at, note. Actual parts used can be minimal work-order line records; inventory purchasing out of scope.
invoices: public_id, unique invoice_number, work_order_id, status(draft/issued/void), totals_mnt, issue snapshots, issued_at/by, void_reason. Draft editable; issued frozen. Not a tax/ebarimt receipt by default.
payments: public_id, amount_mnt positive, method, status(pending/settled), reference, received_at, recorded_by, idempotency_key; payment_allocations: payment_id, invoice_id, amount_mnt; payment_reversals: payment_id/allocation_id, amount_mnt, reason, actor, occurred_at. All mutation paths enforce aggregate settled allocations less reversals <= payment and invoice balance; no arbitrary delete. Simplify one payment per invoice if desired while preserving partial-payment and reversal behavior.
maintenance_plans: customer_id, vehicle_id, source_work_order_id, service/description snapshot, due_date nullable, due_km nullable (at least one), based_on_reading_id, recommendation_source_note, status(active/satisfied/paused/cancelled), supersedes_id nullable, creator, version, timestamps. Completion satisfies an explicitly matched plan; old plan reminders cancelled. Owner transfer stops outgoing reminders for former relationship until reconciled.
communication_consents: customer_id/verified phone binding, purpose(service_reminder/marketing), channel, granted/revoked timestamps, source, policy_version. Initial contact for a submitted request is separate from optional recurring reminder and marketing choices. No prechecked marketing.
notification_outbox: public_id, aggregate_type/id, aggregate_version, customer_id, channel, template_key/version, scheduled_for UTC, lifecycle_stage, idempotency_key unique, payload_minimal, status, attempt_count, next_attempt_at, claim timestamps, provider_message_id, accepted/delivered_at, last_error_code, expires_at.
message_attempts: outbox_id, attempt_number, started/finished_at, adapter, provider_reference, status/normalized error. Avoid message body/phone/OTP secrets in broad application logs.
otp_challenges: phone_hash/normalized phone as needed, hashed_code, session binding, expires_at, attempt_count, max_attempts, consumed_at, resend cooldown. Production secrets never plain logged; purge expired challenges.
audit_events: actor, action, subject_type/id, safe before/after or hashed immutable references, reason, occurred_at, request correlation. Exclude OTPs, credentials, private bearer tokens and unnecessary raw sensitive bodies.
business_settings: brand/public contacts, location, hours source, callout_enabled/area/fee policy, message provider toggle, quiet hours, invoice numbering/tax configuration, readiness state. Typed config/allowlist; settings do not expose secret values. Secrets only env/secret manager.
Laravel framework tables: migrations, jobs, failed_jobs, cache, sessions, notifications as installed. Do not redundantly create equivalent outbox/scheduler tables without need.

4. SCHEDULING INVARIANTS
All reservations are half-open intervals [start, end), end>start, including configured buffers/travel. Conflict when existing.start < new.end AND existing.end > new.start for the same active resource. Adjacent end/start allowed only after buffer expansion. Validate service duration, hours, closures, staff leave, dates and permissions.
For MySQL, transactionally lock stable bay rows and mechanic user/profile rows in deterministic order BEFORE querying conflicts, then create/update all reservations and appointment. Locking only matching appointment rows is insufficient when the slot is empty. Deadlocks get bounded retries; do not retry non-idempotent side effects. Changes are committed before notifications are dispatched.
For SQLite use a connection-appropriate serialized writer strategy (e.g. an explicitly implemented immediate transaction with busy timeout/bounded retries); explain SQLite limitations. Do not assume lockForUpdate has MySQL semantics on SQLite. Keep logic centralized and test with real MySQL for release.
Optimistic version check on editing prevents silent overwrite. Double-submit request confirmation returns its existing result. Invalid drag/drop returns conflict and client reverts. Editing resource/time or cancellation atomically releases/replaces reservations. Cancellation invalidates pending reminders.
Actual occupancy blocks assigning a busy bay even if planned end passed. If planned future reservation conflicts with an overrun, staff sees actionable warning and must reschedule or change bay; no invisible double-capacity. Do not create two authoritative schedules (appointment time and work-order time) that diverge silently.

5. APPROVAL AND FINANCIAL INVARIANTS
Publishing computes content hash/totals server-side and freezes revision lines. Approval locks work order/revision, verifies authenticated customer/order policy, current actionable revision/hash, deadline and amount; records decision once; moves workflow only if allowed. A new revision cannot inherit approval silently. New work outside approved scope blocks until approval or audited authorized override.
Payment settlement/reversal and invoice issue/void use shared transaction actions and idempotency. Use integer MNT and a single rounding implementation for fractional quantities. Never trust posted grand totals. Invoice totals and cash received are separate reporting facts. No binary floating-point money, mutable issued lines or deleted payment history.

6. MEDIA AND PRIVACY
Store originals/processed evidentiary copies privately outside webroot; default keeps a normalized EXIF-stripped evidentiary image and thumbnail. If raw original retained for an explicit business need, separate restricted encrypted/private retention and never serve it to customers by default. Never expose customer files through storage:link. Public brand assets use separate public disk.
Validate extension + MIME + actual decoder result, dimensions and limits. Randomize names, strip location metadata, correct orientation before thumbnail, hash normalized bytes. Avoid SVG uploads to customer media. HEIC unsupported? Reject with clear conversion advice; do not rename HEIC to JPG. Match PHP/Livewire/web server size/time limits; document memory limits and test large-image failure recovery.
Authorize thumbnail, original download, print/export and asynchronous upload finalization. Any temporary signed media route expires, binds the actual record, rechecks auth/access and cannot be replayed by a different account. For private SMS/approval links use short-lived, scope-limited tokens plus phone authentication for sensitive data/actions; no permanent bearer history URL.
Public form uploads are quarantined to the submitting session and idempotency key until finalized; never attach arbitrary file IDs. Delete abandoned temporary files after a configured grace period and preserve linked history. Validate record ownership when moving assets. Customer visibility explicit; staff internal findings remain private.
Ownership transfer: new owner sees only their own eligible work orders; prior owner retains their historical customer snapshots as allowed but receives no new-owner metadata or future maintenance reminders. Export/share of prior history is a deliberate reviewed flow, not automatic. Never merge records by plate alone.

7. REMINDER DISPATCH CONTRACT
Evaluate date rules in business timezone. Km due requires a credible latest reading observed on/after the service baseline. A plan with both date and km triggers on either known threshold, not both. Date-only advance reminders do not invent predicted odometer crossings. If km is unknown, show unknown and rely on date if present.
Outbox idempotency_key includes aggregate id + version + recipient binding + channel + lifecycle stage. DB uniqueness is authoritative, scheduler no-overlap locks supplementary. Evaluate due plans and enqueue after commit; workers claim an item atomically. Dispatch rechecks status, current time, expiry, consent, customer association and aggregate version immediately before sending.
Default quiet hours 20:00–09:00 Asia/Ulaanbaatar, owner configurable. Shift to next permissible send time, then skip if reminder is no longer useful (e.g. appointment already started or cancelled). Sender caps per customer/day and stage; confirmations and essential contact follow explicit purpose rules. Rebooking or a newly satisfied plan cancels old pending reminders.
State machine: scheduled → queued → dispatching → simulated OR provider_accepted → delivered if verified receipt. Failures retry only when known safe; expired/opted-out/stale → skipped. Provider acceptance does not mean handset delivery. Unknown timeout outcome → unknown/reconcile; no blind retry that could duplicate a paid SMS. Use provider idempotency key if supported, query status by correlation ID when available, otherwise manual reconciliation. Exactly-once network delivery is not promised.
SmsProvider contract: send(destination, template payload, idempotency key) returning simulated/accepted/known_failure/unknown plus provider reference; optional receipt/status lookup capability. Log driver only active locally/testing; sanitized audit record says simulated. Real driver is implemented only against chosen provider's current official contract; no guessed endpoints.
Scheduler: evaluate/queue periodically, clock controlled tests; no outbound real SMS from demo. queue:work and schedule:work separate local processes, production persistent worker plus once-per-minute schedule:run cron. Health/readiness shows last successful scheduler tick and worker heartbeat; never infer worker health just from an empty queue.

8. SECURITY, OPERATIONS AND EXPORT
Staff authentication with strong password hashing, generic errors, rate limits and framework session rotation. Owner MFA supported where actual installed Filament capabilities permit and recommended for production. Customer phone OTP cannot reach staff auth. Server policies for every view/action/export; filter table queries AND authorize record actions. Inactive staff lose access immediately/session invalidation as implemented.
Use validated input allowlists, escape notes, validate file paths, CSRF all mutations, no sensitive GET side effects, safe redirect targets, secure cookies under HTTPS, noindex private pages, no PII or private tokens in analytics. Apply honeypot/rate limits first; CAPTCHA optional if actual abuse warrants it.
CSV exports neutralize spreadsheet formula injection and respect role/date scope. Print pages require authorization. Owner bulk exports are audited. Audit retention, temporary upload retention, OTP expiry and request spam cleanup configurable; do not invent statutory retention periods.
Daily DB backup plus private photos and necessary configuration/key recovery plan; encrypted off-server copy; scheduled restore drill on staging. A database-only backup cannot restore photos; missing APP_KEY can break encrypted data. Never put backup archives under public/ or commit .env. Migration rollback is not a substitute for a verified restore plan.

9. PRODUCTION TARGET
One Laravel app served from /public using compatible PHP-FPM and Nginx/Apache. MySQL reachable privately with least-privilege app account, no public phpMyAdmin assumption. No hardcoded server IPs/credentials. Shared deployments preserve storage and correct ownership; no chmod 777. Public brand storage link only if needed; customer private media stays private.
APP_ENV=production, APP_DEBUG=false, HTTPS/session settings, unique APP_KEY, real domain, configured sender/provider and only verified business details. Enable public booking only after readiness check is green. Deploy examples use environment-specific absolute paths placeholders, not assumed live paths. Restart queue workers after new releases; cache config/routes/views only after configuration is correct; test actual upload/queue/scheduler/restore path.
Local SQLite → production MySQL: migrations create schema, an explicit id-preserving data transfer maps SQLite types/JSON/timestamps/booleans, copies private storage, verifies row counts and media hashes, resets sequences, checks constraints and preserves source relationships. Rehearse with demo data. Never simply rename/copy SQLite file into MySQL. Real pilot data requires backup and controlled cutover; production should start clean if only demo exists. Default demo data must never be imported as real customers.
